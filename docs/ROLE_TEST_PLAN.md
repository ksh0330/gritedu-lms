## 1. 목적과 현재 상태

강사 개인정보 분리는 2026-10-19 운영 적용·범위 한정 검증을 마쳤습니다(§19, `MAINTENANCE_LOG.md`). 아래 §15~18의 "운영 미배포"는 각 로컬 QA 당시 판정이며 현재 배포 상태가 아닙니다.

현재 구현되어 보이고 실행할 수 있는 기능을 기준으로 6역할의 실제 업무 흐름과 UI/UX를 함께 검증한다. 새 이상적 권한 모델을 먼저 만들거나 정상 UI를 재설계하지 않는다. 코드·Rules가 우선이고 `PROJECT_STATE.md`, `ADMIN_CMS_STATE.md`, `OPERATION_MANUAL.md`를 대조한다. 문서/실제 화면이 다르면 차이를 기록한 뒤 구현 여부를 판정한다.

이 문서는 매 작업에 재사용하는 실행 계획/테스트 장부다. 결함의 상세 근거와 C1~C7/N1~N10은 `audits/FIRESTORE_SECURITY_CRUD_MASTER_AUDIT.md` §19, 구현·배포·운영 확인은 `MAINTENANCE_LOG.md`에서 관리한다. 같은 발견을 세 문서에 독립 결함으로 중복 등록하지 않는다.

**현재 단계: 사이클 1 비로그인 점검 완료 / 사이클 2 일반 회원·관리자 핵심 업무 Partial / 사이클 3 학생·학부모·강사 읽기 전용 교차 확인 Partial / 관리자 단독 점검 Partial.** 사이클 1 결과는 [비로그인 사용자 실행 보고서](qa/CYCLE1_VISITOR_2026-10-13.md), 사이클 2 결과는 [일반 회원·관리자 실행 기록](qa/CYCLE2_GENERAL_ADMIN_2026-10-16.md), 사이클 3 결과는 [역할별 실행 기록](qa/CYCLE3_ROLES_2026-10-16.md), 관리자 단독 결과는 [2026-10-17 실행 기록](qa/ADMIN_SOLO_2026-10-17.md)에 있다. 사이클 2의 테스트 강좌 카드 문구와 일반 회원 이름은 원복됐고 테스트 수강은 최종 취소됐다. 사이클 3과 관리자 단독 점검에서 운영 쓰기는 없었다.

## 3. 세 사이클 + 관리자 단독 점검

### 추가 검증 요구 (2026-10-16 등록)

- **사이클 3 — 학부모 연동 학생 상태:** 학생 비활성화 시 관계 유지와 상태 표시, 재활성화 시 기존 연결 반영, 삭제 시 연결 해제와 관계 정합성, 다른 관계에 영향이 없는지 확인한다. 구현 여부를 소스와 기존 UI에서 먼저 확인한다. 실제 운영 학생 삭제 및 관계 문서 직접 조작은 하지 않는다. 삭제 행동 검증은 별도 안전한 fixture와 승인된 환경이 마련될 때만 실행한다.
- **관리자 단독 점검 — 현황 불러오기:** 사이클 2에서는 방문 화면만 관찰한다. 명시 조회 화면은 최초 미조회에 주황색 `현황 불러오기`, 성공 후 회색 `새로고침`, 조회 중 진행 표시와 중복 클릭 방지, 실패 시 재시도가 가능한지 확인한다. 자동 조회 화면은 기존 설계를 먼저 확인한다.
- **관리자 단독 점검 — 안내 문구 중복:** 사이클 2에서는 방문 화면만 관찰한다. 표 밖/안의 같은 안내와 단일 섹션 페이지의 소개 중복을 확인하되, 다중 섹션의 상위/개별 설명과 최초 미조회·정상 0건·검색 0건·실패 안내의 구분은 유지한다. `membersMeta`와 회원 표의 빈 행은 확인 예시다.

사이클은 전체 화면을 세 번 반복한다는 뜻이 아니라 **아래 세 업무 조합**이다. 각 사이클 안에서 정상 흐름 → 상태 변경 반영 → 취소/오류/권한 경계 → UI/UX를 확인한다. 강사는 3번 사이클에 참여하며 관리자 단독 점검은 별도 단계다.

### 사이클 1 — 비로그인 사용자 단독

1. 홈 → 강좌 목록/검색/필터 → 상세 → 로그인 필요 안내 → 로그인 진입을 확인한다.
2. 강사진 목록/상세, 공개 시간표 그룹/이미지, 소개, 상담문의·외부 링크를 확인한다.
3. 로그인/가입의 입력 안내·오류·뒤로가기, 보호 경로 진입 시 안내/복귀 경로를 확인한다. 계정생성·OTP 발송은 기본 탐색과 분리한다.
4. 첫 화면/모바일에서 콘텐츠 순서, 공백·잘림·가로 스크롤, 헤더/푸터/팝업/문의 버튼 겹침을 기록한다.

**완료:** 핵심 공개 탐색이 막히지 않고, 보호 화면의 안내가 명확하며 재현 가능한 UI 문제에 화면/조건 증거가 있다. 공개 데이터 장애 주입은 로컬 mock에서 수행한다.

### 사이클 2 — 일반 회원 + 관리자

1. A가 실행 장부에 등록한 테스트 온라인 강좌를 기존 CMS에서 생성한다. 제목·커리큘럼·영상 2개·담당 강사를 지정하고 생성 ID를 기록한다. 공개 노출 조건은 실행 범위에서 먼저 정한다.
2. G가 현재 공개 상세 UI에서 테스트 강좌를 수강신청하고 회원 대시보드 → 학습 화면 → 영상/진도 반영을 확인한다. 현재 UI에 없는 관리자 수동 수강 배정 기능을 가정하지 않는다.
3. A가 해당 회원의 수강 상세를 확인하고 테스트 강좌의 제목/커리큘럼 등 지정 필드만 수정한다. G가 일반 새로고침 후 반영을 확인한다. 자동 실시간 반영을 요구하지 않는다.
4. G가 본인 이름/전화 변경·취소·무변경 저장을 확인하고 A가 해당 상세를 확인한다. C1 구현 후에는 A 대행 수정 → G 반영을 추가한다.
5. 따옴표 제목 재생(N2), 두 탭의 서로 다른 영상 기록(N3), 중복 저장 방지(N4), 실패 안내·정상 빈값 구분(C2/C3/C4/N7/N10)을 해당 구현 단계에 맞춰 확인한다.
6. 수강취소는 테스트 enrollment 1건만 대상으로 한다. 이후 UI가 허용하는 테스트 재신청을 확인하고 계정 자체는 유지한다.

**완료:** 본인 수강·프로필·관리자 상세의 결과가 일치하고, 학부모 전용 UI가 섞이지 않으며, 중복/실패 상태에서 사용자가 다음 행동을 이해할 수 있다.

### 사이클 3 — 학생 + 학부모 + 관리자, 강사 합류

1. A가 테스트 오프라인 반과 필요한 회차를 만들고 S를 배정한다. 테스트 I를 해당 반 및 테스트 온라인 강좌 담당으로 연결한다. 테스트 학생이 온라인 강좌를 수강하는 경로는 현재 UI에 따라 진행한다.
2. S가 본인 대시보드의 오프라인 반 → 회차·설명·영상 링크, 온라인 강좌 → 학습·진도를 확인한다. 자료 첨부/다운로드는 현재 구현 경로가 확인되지 않아 `Not applicable`로 둔다.
3. P가 지정 S의 테스트 정보로 자녀 연결을 실행한다. A는 동일 대상 관계/시도 상세를 확인한다. 이미 연결됐다면 초기 연결 상태를 기록하고 불필요하게 반복 생성하지 않는다.
4. P의 자녀 요약을 S/A 화면과 대조한다. 이름·강좌·반·진도/상태 등 실제 제공 필드만 비교하고, 학부모에게 학생 학습 실행 권한이 있다고 가정하지 않는다.
5. I가 담당 강좌/반을 확인하고 ‘수강생 불러오기’ 후 S가 표시되는지 확인한다. 불러오기 전 검색·필터(N8), 조회 후 검색/페이지, 미담당 테스트 항목 제외도 확인한다.
6. A가 테스트 배정·학생 정보·회차 접근을 한 종류씩 변경하고 S/P/I가 일반 새로고침/기존 명시적 불러오기로 반영을 확인한다. 동시에 여러 관리자가 같은 대상에 쓰지 않는다.
7. A가 테스트 parent link를 기존 UI로 revoke하고 P의 관계/표시를 확인한 뒤 같은 테스트 관계를 reactivate한다. counter와 관계는 기존 transaction 흐름을 사용한다. 학생 상세 A→닫기→B 선택(N9)은 별도 테스트 학생 1명을 사용할 수 있을 때 확인한다.

**완료:** 배정·담당·연결 lifecycle 결과가 각 역할에 맞게 보이고 일반회원/학부모가 혼동되지 않는다. 미연결/미배정/미담당 테스트 계정 또는 별도 fixture가 없으면 해당 경계는 `Blocked` 또는 `Not run`으로 기록하고 실사용자 데이터를 대용하지 않는다.

## 4. 에이전트 분담과 세션

- 메인: 진행/장부/증거 통합, 테스트 데이터 registry, 관리자 쓰기 작업의 단일 소유자. 관리자 페르소나는 별도 리뷰어가 점검할 수 있으나 같은 대상을 동시에 수정하지 않는다.
- 역할 테스터: V, G, S, P, I 페르소나를 사이클에 맞춰 교대 수행한다. 역할 수만큼 에이전트를 만들지 않는다. 메인 단독 수행을 기본으로 하고, 증거가 부족하거나 중요한 판정이 불분명할 때만 해당 분야 보조 리뷰어 1명을 읽기 전용으로 투입한다. 리뷰어는 미실행 사례·반례·원인에 집중하고 기존 결과를 재요약하지 않는다.
- UI/UX는 각 역할 수행과 병행하고, 결과는 메인이 중복 제거한다. 코드 수정 시 기능 영역당 구현 소유자는 한 명이며 다른 에이전트는 읽기 전용 리뷰/검증을 맡는다.
- 같은 origin의 일반 탭은 Auth 세션을 공유할 수 있다. **탭을 나눴다는 이유로 역할이 격리됐다고 간주하지 않는다.** 도구가 지원하는 독립 브라우저 프로필/세션에서 계정과 UID를 확인한 뒤 병렬 실행한다. 분리가 불가능하면 로그아웃 → 다음 역할 로그인 → 역할 확인 순으로 진행하며 다른 에이전트는 증거를 리뷰한다.
- 하나의 브라우저 탭에는 한 명만 입력한다. 역할 전환·viewport 변경·전역 설정 변경도 조정한다. 테스트에 없는 메일함/앱을 탐색하지 않는다.

각 역할 담당자는 사용자 페르소나를 수행하면서 아래 전문가 관점도 함께 기록한다. 보안·개인정보와 성능·비용 관점도 필요한 경우 같은 증거로 검토하며, 전문가 수만큼 에이전트/계정/DB 조회를 늘리지 않는다. 단순 문서 분류는 사용 가능한 경량 모델·Low, 일반 UI는 경량 모델 또는 Sol·Low, 복잡한 코드·권한 분석은 Sol·Medium을 기본으로 하고 필요할 때만 높인다. 지원 모델을 확인하지 않은 설정 변경은 하지 않는다.

| 관점 | 매 시나리오에서 답할 질문 |
| --- | --- |
| PM·학원 운영 | 원하는 업무를 끝낼 수 있는가, 다음 행동/담당자가 분명한가, 누락 정보가 실제 결정에 필요한가 |
| 데이터 | 대상 UID/강좌/반/회차와 상태가 맞는가, 중복·부분 저장·진도 손실·관계 불일치가 있는가, 원본과 snapshot은 어떤 의미인가 |
| 개발·권한·비용 | 비동기 응답/중복 submit/취소/새로고침이 안전한가, UI와 Rules 경계가 다른가, 불필요한 반복 조회가 생기는가 |
| UI/UX·접근성 | 메뉴·용어·순서·안내가 이해되는가, 클릭/키보드/모바일로 완료 가능한가, overlay·focus·스크롤·오류복구가 명확한가 |

결과는 `결함(기대 계약 위반)` / `현재 설계의 한계` / `추가 편의 요구` / `미구현 신규 기능`으로 구분한다. 필요한 정보가 없다는 사용자 의견과 데이터가 잘못됐다는 사실을 혼동하지 않는다.

## 5. 계정·테스트 데이터와 쓰기 범위

사용자는 테스트용 강좌/반 생성, 관리자 배정·정보 수정, 역할별 검토 방식에 동의했다. 실행 시 계정/환경과 아래 registry의 exact 대상을 확정한 후 그 범위의 반복 작업마다 재확인을 요구하지 않는다. 현재는 계정·생성 ID가 없으므로 실제 작업을 시작하지 않는다. 사용자 계정의 실제 역할은 로그인 후 확인하며 계정 정보를 근거로 권한을 새로 확대하지 않는다.

- 시작 시 production `https://gritedu.kr`인지 별도 환경인지, 정적 build/version, Firebase 연결 대상을 기록한다. localhost도 production DB에 연결될 수 있으므로 별도 테스트 DB라고 간주하지 않는다.
- 최소 fixture: 테스트 온라인 강좌 1개(영상 2개), 오프라인 반 1개, 회차 1~2개, 지정 S/G/P/I/A 계정과 P↔S 관계. 다른 학생 상세/미담당 경계가 필요할 때만 추가 fixture를 만든다.
- 표시명은 `QA_<실행일>_<runId>_<종류>`처럼 실수강과 구분한다. 테스트 데이터에는 합성 이름/정보와 사용자가 제공한 테스트 연락 수단만 사용한다. 실학생 개인정보를 복제하지 않는다.
- 생성 전에는 예정 제목·필드·노출 상태를, 생성 후에는 정확한 문서 ID와 변경/복원 값을 장부에 기록한다. 비밀번호·OTP·세션 토큰·전체 연락처는 Git/노션/스크린샷·로그에 남기지 않는다. 자격증명은 직접 로그인 세션 또는 ignore된 로컬 파일을 사용한다.
- course/반의 테스트 이름이나 비공개 UI 상태만으로 보안 격리를 주장하지 않는다. 공개 노출은 실제 구현과 허용 범위를 확인한다. 공개 테스트가 허용되지 않은 항목은 로컬/별도 환경으로 옮기거나 `Not run` 처리한다.
- 공개 사이트 공통 settings(시간표/팝업/사이트/기준값)는 공유 운영 데이터다. 테스트 계정이 있다고 자유롭게 수정하지 않는다. 기본은 조회·취소·로컬 mock이며 실제 저장이 필요하면 exact 문서/필드·노출 영향·원복 값을 실행 범위에 별도 명시한다.
- 기존 사용자/수업·매출·관계에 영향 주는 변경, 신규 관리자 발급, migration/legacy repair, 비밀번호 변경, 이메일 대량 발송, scheduler 수동 실행은 기본 범위 밖이다.
- 종료 시 기존 UI의 archive/비활성화·수강취소·배정 해제·관계 revoke를 사용하고 테스트 계정은 유지한다. 계정/문서 영구 삭제·일괄 cleanup은 자동 수행하지 않는다. 꼭 필요하면 정확한 대상과 영향으로 별도 처리한다. relation 문서 직접 삭제/카운터 수동 보정 금지.

## 6. 매 사이클 공통 UI/UX와 실패 확인

1. 먼저 대표 PC 1440×900과 모바일 390×844에서 핵심 경로를 본다. 이슈가 있는 화면 및 CSS 변경 화면만 360×800, 768×1024, 1280×720, 가로 모드·200% 확대 등으로 확장한다. viewport 검증과 실제 터치/iPhone 검증은 구분한다.
2. 역할에 맞는 메뉴/첫 화면 순서, 제목·버튼·필터·표·상세의 용어·배치 일관성을 비교한다. 역할별 의도된 차이를 강제로 동일화하지 않는다.
3. 모달 높이·내부 스크롤·배경 잠금·닫기/취소/Escape·포커스 복귀·Tab 이동·sticky header/팝업/문의 버튼 z-index를 확인한다.
4. 미조회·로딩·정상 0건·검색 0건·일부 실패·전체 실패·저장 중·저장 성공·저장 실패·저장 후 확인 실패를 구분한다. 운영에서는 자연 발생 상태만 관찰하고 실패/지연 주입은 로컬 mock으로 진행한다.
5. 저장 후 해당 행/상세·검색/페이지 유지, 취소 시 무변경, 오류 시 입력 보존, 새로고침 반영을 확인한다. 기존 explicit-button 조회와 캐시 정책을 테스트 편의 때문에 바꾸지 않는다.
6. 다른 역할 경로/다른 테스트 리소스 진입은 exact fixture로 제한한다. UI 차단·라우팅·Rules 행동을 별도로 기록하고 소스 구조 검사만으로 권한 검증 통과를 선언하지 않는다.
7. 입력·검색·필터는 대표 사례만 최소 횟수로 실행한다. 동일 DB 목록을 에이전트마다 반복 로드하거나 비용 측정을 위해 전체 collection을 조회하지 않는다.

문서 단계의 기본 검증은 `npm run check:rules:strict`, `npm run check:functions:strict`, `git diff --check`. 구현 시 기존 `test:firestore-crud` 등 관련 테스트와 build/verify를 변경 범위에 맞춰 선택한다. 배포는 정적/Rules/Functions를 구분하고 변경 없는 backend를 배포하지 않는다.

## 11. 신규 기능 기획 — 관리자 온라인 배정과 4가지 강좌 유형

**상태: 사용자 요청 기록 / Planned / 구현·Rules 변경·배포·데이터 전환 전.** 현재 사이클 밖의 신규 요구이며 기존 N1~N10 오류 10개에 합산하지 않는다. F1/F2는 하나의 제품 흐름으로 연결하되 권한·호환성 설계 후 작은 단계로 구현한다.

### 11.1 현재 구현과 신규 요구의 차이

- 현재 `public`은 공개 학습 링크/목록을 제공하며 비로그인도 열 수 있다. 공개 영상에 enrollment 기반 개인 진도를 자동 요구하지 않는다.
- 현재 `memberOnly`는 학생·일반회원의 자가 수강신청 후 active enrollment로 학습한다. 학부모는 자가신청 불가. 관리자 학생 온라인 배정 UI는 없다.
- 현재 `paid`는 유료/미사용·결제 준비 중 경로다. 신규 지정학생 유형으로 재해석하거나 기존 값을 자동 전환하지 않는다.
- `status`(작성/게시/보관), `visibility`(목록 노출), `accessType`(접근 방식)을 하나의 임의 4값으로 덮어쓰지 않는다. 아래 네 개는 사용자에게 보일 **상품/접근 유형 제안**이며 실제 필드·enum·호환 읽기는 기술 설계에서 확정한다.
- 현재 관리자 게시 저장은 visibility를 public으로 정하는 경로가 있고(`admin-courses.js:661-667`), 알 수 없는 accessType은 public으로 fallback한다(`utils/course-readonly.js:293-300`). 새 네 유형을 단순 옵션 추가로 저장하지 않고 구 클라이언트/기존 저장 동작과 호환되는 순서를 설계한다.

### 11.2 네 가지 유형 — 정책 초안

| 유형 | 학습 대상 | 수강 시작 | 일반회원·학부모·비로그인 경계 |
| --- | --- | --- | --- |
| 공개 | 누구나 | 현재 공개 학습 흐름 유지 | 비로그인 열람 유지. 회원 개인 진도 신규 보장은 별도 범위 |
| 회원전용 | 로그인한 학생·일반회원 | 현재 자가신청 유지 + F1 관리자 학생 배정 | 학부모는 자녀 요약만, 비로그인은 로그인 안내 |
| 회원전용·지정학생(관리자 관리) | **관리자가 배정한 active 학생만** | 학생 자가신청 없이 본인 대시보드 학습하기. 미배정 학생은 자가신청 불가 | 일반회원 전체에 개방하는 의미로 해석하지 않음. 학부모는 연결자녀의 허용된 요약만, 학습권한 상속 없음. 목록/소개 노출은 별도 노출 정책으로 결정 |
| 비공개(관리용) | 초안: 관리자와 담당강사 확인/미리보기 | 신규 신청·배정 학습은 막음 | 학생/일반회원/학부모/비로그인 학습 불가. 기존 enrollment·진도는 보존. 담당강사 미리보기와 기존수강 일시정지/복원 의미는 구현 전 확정 |

‘회원전용+일부 허용 학생’은 일단 **로그인한 지정학생만 학습**하는 뜻으로 정리한다. ‘일반회원 전원 + 일부 학생’이라는 OR 정책은 제안하지 않는다. 비공개와 작성/보관의 차이, 지정학생 강좌의 목록/소개 노출, 기존 수강자에 대한 유형변경 효과는 아래 결정 장부에서 확정한다. 초안 문구를 확정 권한 계약으로 배포하지 않는다.

### 11.3 F1 — 온라인 강좌에서 학생 수강 배정

목표는 오프라인 입반처럼 관리자가 강좌 안에서 학생을 선택해 수강을 시작시키는 것이다. 지정학생도 별도 신청 없이 기존 대시보드/학습 경로를 사용한다.

1. A가 테스트 대상 온라인 강좌의 기존 상세/수강생 영역에서 학생 배정 진입 → 기존 학생 목록 패턴에 맞춰 검색·선택 → 대상 확인 → 배정한다. 새 전용 대시보드나 Function은 1차에 추가하지 않는다.
2. 선택 대상은 1차 **학생 계정만**이다. G/P/I/A를 수강자로 배정하는 요구는 포함하지 않는다. 강좌별 조회와 현재 페이지 대상의 필요한 정보만 읽고 전체 enrollment scan/행별 N+1/키입력 query를 새로 만들지 않는다.
3. 동일 학생·강좌 중복 배정은 1관계만 유지한다. 기존 active는 이미 배정 안내/무변경, 기존 취소/해제 관계는 명시 재활성화 정책에 따른다. 기존 진도는 기본 보존하고 초기화는 별도 요청 동작으로 분리한다.
4. 배정 후 S 대시보드에 강좌가 보이고 학습하기로 진입하며 A/I의 해당 강좌 수강생 조회에서도 확인된다. P는 연결된 S의 현재 온라인 요약 범위만 확인한다. 반배정과 온라인 enrollment는 별도 관계다.
5. A는 정확한 학생·강좌의 배정을 해제/재활성화할 수 있어야 한다. 지정학생 유형은 해제 후 새 학습 접근을 차단하고 기록을 보존하는 방향으로 설계한다. 기존 open 회원전용에서는 해제 후 학생이 다시 자가신청할 수 있으므로 F1만으로 강제 차단을 보장하지 않는다. 이미 열린 외부영상 회수까지 보장하지 않는다.
6. 기존 자가신청의 deterministic ID/legacy enrollment 호환, 해제된 관리배정을 학생이 자가신청으로 복구할 수 있는지, 일반 회원전용에서만 학생 자가취소를 유지할지 기술·운영 정책을 결정한다. 지정학생 강좌에서는 학생이 관리 배정을 생성/복구/권한 변경할 수 없어야 한다.

### 11.4 F2 — 실제 접근 경계와 호환성

현재 `firestore.rules:777-779`는 courses 전체 공개 읽기이고 강좌 문서에 weeks/영상 URL이 함께 있을 수 있다. UI에 지정학생/비공개 표시만 추가해도 내용·영상의 실제 비공개가 되지는 않는다. 현재 owner enrollment create 검사(`:562-573,791-792`)도 새 강좌 정책을 강제하는 설계가 필요하다.

- 공개 목록/소개 정보와 보호할 커리큘럼/영상 정보를 구분하고, 공개 문서에는 보호 URL을 넣지 않는 목표로 **영향 강좌·소비 화면·exact 필드**부터 설계한다. 구체적 저장 위치/스키마를 이 계획만으로 확정하거나 migration하지 않는다.
- 지정학생의 self-enrollment/취소 후 재신청·revoke 후 재활성 우회, 다른 학생 UID를 넣는 쓰기, 직접 학습 URL/SDK 접근까지 Rules로 검증한다. 화면 버튼 숨김은 권한 검증이 아니다.
- owner 전체 update/delete 후 recreate와 담당강사 update의 권한필드(userId/courseId/status 등) 변경 경로도 함께 검토한다(`firestore.rules:794-800`). 한 종류의 create 차단만으로 지정학생 정책이 완성되지 않는다.
- 담당강사 read, 연결학부모 요약 read, 기존 자가신청/진도 update·학생 수강취소를 함께 검토한다. F1에서 admin create가 이미 허용된다는 사실만으로 F2 완성을 주장하지 않는다.
- 기존 public/memberOnly·URL·DOM·enrollment 읽기 호환을 유지하고 기본값 누락/legacy/paid를 임의 재해석하지 않는다. 기존 진도·수강·반배정·관계를 삭제하지 않는다.
- 공개 필드 감사의 기존 보류는 **F2 실보호에 필요한 정확 범위에서 재검토할 신규 의존성**으로 기록한다. 전체 instructor 감사·오프라인 Rules 보류를 자동 해제하지 않는다.
- 신규 Function/listener/요약 collection 없이 기존 Firestore 구조에서 가능한 최소안부터 평가한다. 필요 Rules/데이터 경계가 정해지기 전 F1/F2 전체 구현·배포 일정을 확정하지 않는다.
- Firestore의 보호 정보 읽기 제한은 이미 알려진 YouTube/MP4 URL의 외부 공유·재생 자체를 회수하는 기능이나 DRM이 아니다. 해당 외부 호스트 제어는 이번 신규 요구 범위에 포함하지 않는다.

### 11.6 결정 장부와 진행 위치

| 결정 | 제안/확정 여부 |
| --- | --- |
| 지정학생 학습 대상 | 학생만, 관리자 active 배정 필요라는 해석안. 운영 전 최종 정책표 확정 |
| 목록/소개 노출 | 학습 권한과 별개. 현재 visibility/status와 호환하는 기본값 결정 전 |
| 비공개·담당강사 | 관리용/담당강사 미리보기 제안. 실제 미리보기 범위·기존수강 정지/복원 결정 전 |
| 관리배정의 취소/재배정 | 지정학생의 권한 자가복구 금지. 일반 memberOnly의 학생 취소·관리자 재배정과 진도 보존 세부 결정 전 |

### 오프라인 회차 권한 불일치의 별도 개선안 (읽기 전용 조사)

현재 학생 UI는 active 반 배정 이후에도 `joinedAt` 이전 회차와 `offlineSessionAccess.status: revoked` 회차를 숨긴다. 하지만 `firestore.rules`의 `offlineClassSessions/{sessionId}` read는 active 반 배정과 `published`만 요구하므로 해당 회차 문서의 영상 URL을 직접 읽을 수 있다. 관리 UI의 grant/revoke 표시는 이 Rules 경계를 강화하지 않는다. `md/DATABASE_SCHEMA.md` §6에도 같은 Confirmed defect가 기록돼 있으며, 이번 4차에는 Rules·스키마·운영 데이터를 바꾸지 않았다.

별도 작업에서는 먼저 운영 sessionDate(`YYYY-MM-DD`)·joinedAt(timestamp)·기존 canonical/legacy access 문서의 정확한 대상 수와 query shape를 읽기 전용으로 확인한다. 그 뒤 UI의 기본 허용/수동 허용/수동 차단 우선순위를 서버 권한 판정에 투영할 방식을 설계하고, URL을 포함한 회차 읽기와 목록 query가 모두 같은 판정을 따르도록 한다. sparse 예외와 legacy 중복, 반 제거, 강사·관리자 접근을 Emulator에서 검증한 뒤 호환 데이터 확인→권한 전환 순으로 진행한다. 새 Function 또는 대량 projection은 비용·운영 승인 전에는 추가하지 않는다. 구체적 Rules 변경과 배포는 owner 별도 결정 사항이다.

과거 `qa/` 실행 보고서는 당시 증거로 보존한다. 현재 상태·남은 항목은 이 §22와 `docs/MAINTENANCE_LOG.md`에서 추적해 같은 감사 문서를 새로 만들지 않는다.

다운로드 범위는 화면의 현재 **적용된 검색·필터 결과 전체**이며 현재 페이지만이 아니다. 추가 조회가 없는 강사·강좌·계정 파일은 바로 생성한다. 학생·회원·반은 대상 수와 추가 관계 종류를 하나의 확인 모달에서 안내한 뒤 관계 collection을 UID/반 ID 10개씩 `in` 조회한다. 각 요청은 200건으로 제한하고 다음 문서부터 이어 읽는다. 관계 종류당 누적 5,000건을 넘거나 어떤 묶음 조회라도 실패하면 파일을 만들지 않는다. 관련 프로필/강좌/반 문서는 ID 10개씩 묶어 읽는다. 대상 학생 25명이면 첫 관계 페이지 기준 3종 × 3개 = 9개 관계 query이고, 회원 파일은 연결 자녀 수에 따라 자녀 수강·입반 query가 더해진다. 데이터가 많으면 관계 페이지 query가 더 필요하다. 기존 작은 master 목록 로드는 화면의 원래 동작이다. 보호 콘텐츠 URL, 비밀번호, 토큰, 세션 자료는 XLSX에 없다. 누락된 참조의 이름은 `확인 불가`; 관계 snapshot fallback을 사용하면 출처를 표시한다. 여섯 XLSX 버튼은 초기·로딩·실패·결과 0건에서 비활성화하며, 일반 결과는 화면 상단 중앙의 공통 토스트를 사용한다.

합성 handler 테스트는 전체 필터 15행, 같은 이름의 서로 다른 UID, 한 학부모의 자녀 2명, 학생의 복수 강좌·반·보호자, active/revoked, 누락 강좌, 빈 관계, 조회 전/검색 0건/실패, 5,000건 초과 차단, 단일 파일/다중 시트/수식 문자열 보호를 확인한다. 실제 SheetJS 모듈로 만든 `.qa-local/synthetic-admin-relations.xlsx`를 재읽어 시트 4개, 자녀 관계 3행, 자녀 수강·입반 각 2행, 전화번호 문자열 앞자리 0, 동일 이름의 UID 구분, 수식 셀 부재를 확인했다. 이 파일과 검증 스크립트는 Git ignore 경로에 있다. 관리자 실계정의 전체 컬럼·Firestore 인덱스·권한·다운로드 시간·대량 데이터 검증은 **Not Run**이다. 운영 환경에서 정확한 비용과 P95는 측정 전이다.

Strict 빌드의 관리자 여섯 화면을 1440/768/390px 로컬 브라우저에서 확인했다. 각 화면의 초기 `엑셀` 버튼은 disabled였고 문서 가로 넘침은 0px이었다. 계정 버튼은 기본 탭에서 숨겨진 상태이므로 높이 측정 대상에서 제외했다. 실제 조회 성공·실패 후 버튼 전환과 로그인된 상세 데이터 행은 인증 fixture가 없어 브라우저에서 **Not Run**이며 상태 분기 합성 테스트만 통과했다. 별도 로컬 합성 페이지에서 공통 토스트를 실제 클릭해 390px에서는 중앙 x=195px·너비 358px·상단 약 28px, 1440px에서는 중앙 x=720px·너비 420px·상단 약 85px과 높은 표시 계층을 확인했다. 같은 오류 메시지 연속 클릭은 토스트 1개로 억제됐다. 이 합성 페이지는 배포 산출물에 포함되지 않는 로컬 QA 파일이다.
